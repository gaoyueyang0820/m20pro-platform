# 灯语与实验问候

默认问候只设置头灯和尾灯，结束后请求恢复厂商默认灯效。点头（Pitch）和起伏（Z）保留为显式选择的实验入口；它们的实际效果尚未由本 PR 的离线测试证明。

| 文件 | 职责 |
| --- | --- |
| `greeting.py` | 纯协议组包、20 Hz 请求序列、反馈检查与显式所有权恢复辅助函数 |
| `greeting_runtime.py` | 平台会话、控制权、取消与连接变更处理 |
| `m20/m20_greet.py` | 独立标准库 CLI，默认仅灯语 |
| `tests/test_greeting.py` | `unittest` 协议、数值边界与反馈回归 |
| `tests/test_greeting_cli.py` | 模拟时钟/连接的 CLI 生命周期与报文接收回归 |
| `tests/test_greeting_runtime.py` | 平台真实入口配合模拟链路的控制权回归 |

## 使用

以下是真机命令示例，不属于离线验证流程。运行独立 CLI 前，应停止平台自主任务和其他运动客户端；独立 UDP 客户端没有跨客户端控制权仲裁能力。`--ip` 要填当前可达的机器人地址。

```bash
python -m m20.m20_greet --ip 10.21.31.103 --status
python -m m20.m20_greet --ip 10.21.31.103
python -m m20.m20_greet --ip 10.21.31.103 --style flow --seconds 4
python -m m20.m20_greet --ip 10.21.31.103 --nod
python -m m20.m20_greet --ip 10.21.31.103 --bob
python -m m20.m20_greet --ip 10.21.31.103 --nod --stand
```

`--status` 只请求状态和维持反馈心跳；不会设置灯光或发送运动轴。灯语不要求起立，也不发送任何轴、使用模式或步态命令。`--stand` 只在同时请求实验动作、反馈为趴下状态时允许请求起立；不主动切换使用模式或步态，必须读回新的 `MotionState=17` 才继续。

灯语时长限定为有限的 0.05～60 秒。灯光 `Cycle` 是整数秒，本实现限定 1～60 秒；60 秒是应用边界，不是厂商协议最大值。默认呼吸/闪烁周期为 1 秒。结束关闭自定义灯语会返回厂商默认灯效，**不能恢复执行前另一客户端设置的自定义灯光**，因为这里没有读取它的接口。

## 协议依据和边界

依据项目归档的 2026-10-23 M20 官方资料，两套《软件开发指南》及 Android 协议固定快照互相核对。归档资料位于项目知识技能中；原项目文件位置如下：

| 结论 | 原文 |
| --- | --- |
| 自定义灯语为 `Type=1101, Command=14`；两个 `Led` 条目分别对应头灯、尾灯；`CustomMode=false` 返回默认灯效 | `M20Pro文档学习/官方支持站/docs/259675872_软件开发指南.md` §1.2.7；旧版 `docs/04_软件开发指南.md` 自定义灯语 |
| 归一化轴为 `Type=2, Command=21`，范围 [-1,1]，建议至少 20 Hz；只适用于常规/辅助使用模式 | `259675903_运动控制（basic_server_协议）.md` §4.4 |
| `MotionState=1` 是起立过渡，随后进入 `17`；`17` 才是移动和步态切换状态 | 同上 §1 运动状态定义 |
| 四种公开移动步态只明确支持 X/Y/Yaw 有效；不能据此保证站立时 Z/Pitch 有效 | 同上 §4.4 注意事项；《软件开发指南》运动控制 |
| `0x1003` 是标准楼梯步态，属于公开移动步态，不能解释为“无法行走的姿态调节模式” | 同上 §2 步态定义 |
| 使用模式切换会将步态重设为基本步态，只有拥有该变更且当前状态仍符合预期时才可考虑恢复 | 《软件开发指南》使用模式切换；Android `m20-android-sdk` 固定提交 `01e1ec7e3c75e76f01bc1325a450cffaff13cebd` 的对应接口 |

所有点头/起伏帧请求 X、Y、Yaw 为零，**这不是绝对无位移的保证**：惯性、外力、机器人控制器行为及其他客户端仍可能导致位移。官方的 500 ms 指令丢失保护描述的是减速与进入安全状态；0.4 秒零轴序列既不是该保护的时间覆盖，也不是停止确认。

## 反馈与取消

实验动作开始前以及每次发送前均检查：基础状态不超过 2 秒、运动反馈不超过 0.5 秒、HES 明确为 0、未休眠、状态为 17、已知可控模式与步态；LinearX、LinearY、OmegaZ 必须存在、有限且低于静止阈值。缺失反馈不能默认为零，NaN 不能通过比较检查。原始 Items 调用检查函数时必须显式提供可信接收年龄；完整记录优先使用单调时钟时间戳。

CLI 分别保存 `(Type, Command)` 的接收时间，只接受配置 IP 的回包；心跳和其他命令不会刷新旧运动反馈。每帧重新核对模式、步态和朝向是否变化，调度延迟超过 150 ms 则取消，不集中补发积压动作。正常序列后的零轴请求仍需要后续新运动反馈才能报告静止确认。

取消或异常只清理本次实际发送过的请求：发送过轴时立即请求零轴，设置过灯语时请求默认灯效。纯灯语、状态查询、动作前检查失败不会额外发送轴。CLI 的 Ctrl+C 返回 130，执行失败返回 1；收尾失败不会掩盖原来的中断。连接断开时无法保证清理命令已到达或机身已经停止。

问候不主动切换使用模式和步态，因此状态发生变化时取消并保留新状态，不猜测是问候导致，更不无条件“恢复”旧状态。`restore_commands` 默认返回空；它只为显式声明本操作已写入的变更、当前仍匹配预期的调用方提供计划。实际发送者还须在每一步发送前重新核对控制权与新鲜静止反馈。

平台会话使用平台已有控制权与停止入口；取消、重连或其他操作接管后，旧线程不得再发送迟到动作或清理新连接。演示姿态是合成展示，不代表机器人执行验证。

## 离线验证

```bash
python -m unittest discover -s tests -p 'test_greeting*.py' -v
```

协议和 CLI 测试只需标准库；平台运行测试使用项目已有依赖。CLI 测试替换连接和时钟，不创建真实 UDP 连接。覆盖缺失/NaN/过期状态、错误来源 IP、Type/Command 混淆、站立过渡、操作者改模式/步态、中断、节拍延迟及清理异常。本 PR 审查阶段未连接、部署或控制机器人；没有新增真机效果承诺。
